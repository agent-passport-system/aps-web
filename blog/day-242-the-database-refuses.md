# Day 242: a read-only setting the client could switch off, and a second implementation that matched 76 of 76

**The label is policy, the database is the boundary.** mcp-clickhouse v0.7.0 runs every SQL statement through one tool, `run_query`, so the [APS ClickHouse example](https://github.com/agent-passport-system/aps-clickhouse-mcp-delegation) now reads the scope from the statement. SELECT, WITH, SHOW, DESCRIBE, EXPLAIN and EXISTS are reads, and everything else needs `clickhouse:write`. That check reads one keyword, so it cannot be the boundary. My first version leaned on `readonly=1` in the client settings, and testing showed a per-query `readonly=0` overrides it. mcp-clickhouse sends exactly that when writes are enabled. A read delegation now runs as a ClickHouse user created with `readonly = 1 READONLY` and only a SELECT grant, so the server refuses a write the label missed.

**Review found two holes before the push.** A destructive tier I had added let `DROP/**/TABLE` fall through to plain write, so I removed the tier. The next round found that `files:read` next to `clickhouse:read` picked the full user. The full user is now chosen only when the delegation authorizes `clickhouse:write`. The demo asserts every expected outcome and exits 1 on any mismatch, and I ran it broken three ways to see it fail. The [comment on #155](https://github.com/ClickHouse/mcp-clickhouse/issues/155#issuecomment-6231297139) says what each layer does.

**76 of 76, with the limits stated.** Toshi asked for a second implementation of MUSUBI settle core v0 on [horizon-shield #49](https://github.com/ogasurfproject-jpg/horizon-shield/issues/49). I wrote one from the spec without reading his code. All 76 vectors match his expected outputs on the eight core fields, and the outputs were frozen and hashed before any comparison. My first comparator found disagreements and still exited 0, which a reviewer caught, so the published one exits 1. The code was written with AI, I ran it myself, and APS is a party to the baseline contract, so this is a second implementation and not independent verification. It is at [aeoess/musubi-settle-core-check](https://github.com/aeoess/musubi-settle-core-check). One question went with it. My classifier counts an approval that carries only a signature field, while section 10.4 names only `sig_b64`, so I asked which one he intends.
