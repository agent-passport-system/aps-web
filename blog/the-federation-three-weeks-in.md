# The federation, three weeks in: twenty projects on one map, a common port, and a pilot on ourselves


The dev logs on this page say what changed in the code. This post is about the thing they keep mentioning in passing, because it is the most interesting work happening around APS right now and I have barely written about it.

**The proposal.** On September 29 I opened [#177](https://github.com/aeoess/agent-governance-vocabulary/issues/177) in the vocabulary repository with a proposal for a federation of independent open source projects that build neutral infrastructure for AI agents. Many of us find the edge cases, write the specs and build the primitives, and then the ideas travel faster than the projects that made them. The work survives and the project may not. An agent's transaction needs authority, enforcement, payment, a receipt and verification, and no single small project should have to own all of it, so each of us keeps building one piece and makes it readable to the others. The rules came first: no required central protocol, no pay to play, no exclusivity, and nobody loses ownership of their project. I asked four questions: your project, one thing it produces or consumes that another project could verify, one boundary you would like to make interoperable, and what you would want from a federation like this. Ten projects answered on the first day. Several said they would talk about one technical boundary and nothing about structure or money, and one maintainer said federation was the wrong word for what we were describing. I kept the word and took the point. Answering does not enroll anyone.

**We started by checking each other's work.** The first thing we built was a [map](https://github.com/aeoess/agent-governance-vocabulary/pull/179). Each project is a node and describes itself. A line between two projects exists only when one project ran another's artifact and the run is recorded, so the map shows what has been tested and nothing else. The draft has twenty projects and tools and seventeen of those lines. When a project asks me to add it, I ask it to write its own entry, because an entry I write about someone else is my claim and not theirs. We also keep the labels strict. When I run another project's fixture with my own code, it is a second implementation, because APS has a stake in the result. An independent run is one by someone who wrote none of the code. Pico, the agent that runs Agent Errata, ran Veritas Acta's E6 fixture that way, found two defects, and Acta shipped v1.1.0 with both fixed. Another project's independent run then passed on v1.1.0.

**A common port.** On October 7 I published [federation-port](https://github.com/aeoess/federation-port), one open contract that a customer would integrate once and other projects plug into. Within two days REMORA, invinoveritas, Horizon Shield and AgentAvow each wrote an adapter for a check their own project already performs, without changing the core. On October 9 three of them ran together with an APS component in one workflow, all four required. REMORA also modelled the contract in TLA+ and sent four findings with a patch, which is the kind of help that makes a shared contract better than one I could write alone.

**I stopped being the gate.** Two decisions made it a group rather than my project with guests. First, nobody needs my permission to run anything. If the artifact and the procedure are public, anyone runs them, and review applies only when a result goes into a shared record. Otherwise I am a bottleneck in the middle of something meant to be neutral. Second, I administer the repository, but an admin merge should not count as the group agreeing, so I asked in [#185](https://github.com/aeoess/agent-governance-vocabulary/issues/185) how changes to shared files should be decided. All seven responses supported the same process: a review window, one approval from a maintainer of another project, one voice per project, and no approving your own change. [#201](https://github.com/aeoess/agent-governance-vocabulary/pull/201) writes it down.

**The decisions from the last two days.**

The agreed windows were seven days for ordinary changes and fourteen for principles. That is right for changing the principles and too slow for a group at this stage that ships every day. I proposed windows by type of change, 48 hours for verified progress and fourteen days kept for the principles and the process itself. A project's own entry, claims and keys still need that project's confirmation on every change, with no exceptions. For adopting the file I asked for a one-time 72-hour window, and only explicit agreement from everyone who answered #185 counts. Silence does not. Frequency agreed and invinoveritas approved the revision.

I also held back one of my own changes. Veritas Acta's E6 line is ready to be marked independently reproduced. On #177 I had promised that changes to E6 go through the shared process once it exists, so the update waits for #201, even though I prepared it and the evidence is there. If I skip the rule the first time it slows me down, it was never a rule.

Then the lead went quiet. On October 12 a store asked through our pilot form for agents that buy, order and refund through its existing checkout. It stopped replying. I told the group instead of letting it fade, and asked every project to put a pilot form on its own site and treat cold emails as possible leads, passing a lead to whichever project fits it better. One lead is not a pipeline, and twenty projects can find more than one.

**A pilot on ourselves.** In the same message I suggested we stop waiting: an agent with a delegated budget pays another project for a real service on a testnet. Four minutes later Toshi offered both halves. Horizon Shield's estimate audit, which homeowners in Japan already pay for, would be exposed as a metered call, and MUSUBI, his settlement layer, would handle authority and payment. Then babyblueviper1 named the step none of us had. Payer and payee can both be honest and the buyer can still get the wrong audit, so invinoveritas will commit the buyer's acceptance criteria before the call and sign a record afterwards of whether the audit met them, with a key that belongs to neither side. Toshi opened [horizon-shield #51](https://github.com/ogasurfproject-jpg/horizon-shield/issues/51) with the frozen inputs: one audit call, three sets of receipts on the same request, and three cases. A call within budget, a call whose deliverable fails acceptance on purpose, and a second call over the budget.

The decision I care about most is what I did not argue. Several projects in #177 can produce this kind of receipt, and nobody knows yet which approach is best or how they really differ. So the same call runs through more than one of them, each project keeps its own verifier, and the comparison is written per run before anyone ranks anything. What we learn there decides what we standardize, instead of whoever argues best deciding it in advance. APS takes the authority side on the second run, and I run the payer agent. The spending limit is a signed delegation, a gate checks every call before it goes out, and every payment names exactly the request it pays for. The units are JPY-testnet play units, not money. Rehearsing it locally showed that my own payer could pay twice for one call, which [Day 243](/blog.html#day-243-signed-without-checking) covers, and it is fixed and in review before the first testnet payment.

**What is not true yet.** There is no store and no customer. No real money has moved. The map and the shared principles are still open pull requests, and the process in #201 is not adopted. The economic idea behind all of this is mine and only an idea so far: value shared between projects in proportion to what was actually used, attributed per action from receipts. AgentAvow drafted the first attribution record for one action, and we agreed on the order, record first and money later.

What is true is that more than twenty people, and some of their agents, have spent three weeks running each other's code in public, posting the failures with the fixes, and writing their own rules for how they decide together. Next on #51 are testnet payments for the first two cases, then our keys and a date. If you build a piece of this stack, describe your project on #177 in your own words.
