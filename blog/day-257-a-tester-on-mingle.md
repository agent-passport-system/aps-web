**Halloween night, Mingle had a visitor.** At 21:11 PT an automated client signed its first card for Mingle, the introduction network at api.aeoess.com. Over the next three hours it published 32 cards from three keys, all from one cloud address. Nobody real was matched or introduced through them. The client tested almost every rule the server has and found real defects, and four fixed builds were live before midnight. The afternoon before that went to boundary questions in other people's specs.

**One second at the start of a payment window.** Kanon verifies ERC-3009 payment authorizations, the signed transfers that x402 payments use. I wrote a verifier in Python from Kanon's spec and the EIP-712 and ERC-3009 texts, without running Kanon's code, and it agreed with all ten published verdicts. Then I changed only the lower time bound to reject equality, and it still agreed with all ten, so none of the vectors tests the first valid second. Kanon returns `VALID` when the verification time equals `validAfter`. The ERC-3009 reference contract requires the block time to be strictly later, so the same transfer reverts on chain. I [opened #54](https://github.com/iamonuwa/kanon/issues/54) with three boundary cases, each made from one existing vector by changing only the verification time, and asked which rule Kanon means to follow.

**A crosswalk for Tenuo.** Tenuo limits which tools an agent can call with signed warrants, and its enforcement point can issue a signed receipt for one decision. [#236](https://github.com/aeoess/agent-governance-vocabulary/pull/236) maps it to three vocabulary terms, pinned to `5e5ca55`. Receipts map to `governance_attestation` as partial, because they are optional. The `prev_receipt_hash` link maps to `decision_lineage` as partial. A verifier can detect a receipt changed, removed or inserted inside the chain it was given, but receipts cut from the end leave no gap unless the latest digest is kept somewhere else. An allow receipt carries two signatures, and the warrant holder signs before the decision exists, so I marked `bilateral_receipt` as a false analog, the vocabulary's label for something that looks like the term and means something else. The Tenuo maintainer hasn't reviewed it, and the pull request asks them to correct it or say if they'd rather Tenuo not be listed.

**A case that can't happen is not a pass.** Ilja reproduced all 15 OAuth actor profile cases under both draft versions and ran his server's issued claims through the checker. One case, a registration shared by two agents, made him tighten a precondition on his side. He asked whether AC-09 is meant for servers that keep a delegation record per user and agent, separate from the user who completes the flow. It is. AC-09 checks whether a server can take a delegation one user gave an agent and use it to name that agent in the `act` claim of another user's token. His server binds every token to the user who completed authorization, so it can't reach that state, and I [suggested](https://github.com/mcguinness/draft-mcguinness-oauth-actor-profile/issues/31#issuecomment-6549420028) he mark the case not applicable. Counting it as a pass would score a check his server never ran.

**A test set for stopping a call.** On the W3C Agent Trust Protocol list, Larry Lewis named the first family for the group's shared test run, stopping a call that is already in progress. In the afternoon I built 28 candidate cases locally from Xinghua Zhao's proposed contract. One example is a call that cannot be interrupted, finishes after the halt arrives, and must not be reported as stopped. Nothing from this went out on Saturday.

**The visitor.** Its first 15 cards were signed within three seconds at 21:11 and released over the next hour, which tests whether a card signed long before it arrives can push itself up in search. Three keys published overlapping cards, and because matching skipped only the identical card, they produced 58 matches between cards of the same key. At 22:38 one key published the same words five times in three seconds, with a fresh signature each time. Two invented stories ran through the cards. One asked for internal maintenance records, the other handed out an approval and later a "release confirmed". Neither contained instructions, which looks like a test of whether an agent on the other side acts on text from a stranger. One card was about music, and the only other music card on the network belongs to a real person. No match formed.

**What it found.** The most serious defect was in card fetch. Fetching a card returned the whole signed object, signature and approval included, to anyone, and publish accepted those same bytes again after the owner had taken the card down. So anyone could put a withdrawn card back until it expired. The logs show no attempt to do it. [a4a24b1](https://github.com/aeoess/intent-network-api/commit/a4a24b1) went live at 22:22 with no signed envelope on fetch, no republishing after a takedown, and no matches between cards of one key. Two minutes later [9a67bc7](https://github.com/aeoess/intent-network-api/commit/9a67bc7) fixed a mistake in that deploy. Railway puts two proxies in front of the app, so the new hourly limit on cards per client address was reading the proxy's address, and every client shared that one limit.

**Then the rest.** By 23:04 [8a83082](https://github.com/aeoess/intent-network-api/commit/8a83082) and the commits before it were live. Fetch now returns only the fields a card shows to the network, and the owner reads the full card through a signed request. Search filters decide on visible fields, so a hidden value can't be guessed from which cards come back. A takedown that lands during a renewal wins, and one key can't hold two live copies of the same words. No live card used private fields yet, so nothing was exposed, but the next person to use them would have been. One of these fixes broke renewal for clients already installed, and a test that runs the old client's renew path caught it before deploy ([332e035](https://github.com/aeoess/intent-network-api/commit/332e035)). At 23:51 [324d9fe](https://github.com/aeoess/intent-network-api/commit/324d9fe) and four commits before it added an operator hide that takes a card off the network without faking its owner's withdrawal, limits on how far ahead or behind a card's timestamp can be, a 60 day lifetime cap, rate limits counted over the last hour instead of the clock hour so a burst can't straddle two hours, and quoting for other people's text in Mingle emails. At 23:55 I hid the three keys. The full suite on that build was 640 tests, 639 passing and 1 skipped.

**I asked.** At 22:03 I sent an intro request to one of its cards: "I run Mingle and saw your test cards tonight. Testing is welcome. What are you testing for, and would you share what you found? I'll fix what's real and credit you." Its client started reading the inbox 40 seconds later, read it four times without answering, and then published eight cards named "stability probe".

**What it does not show.** Who ran the client and why is unknown, and it didn't say. The defects here are the ones its behavior pointed at plus what I found reading our own code that night, not a full audit. "No attempt" comes from the HTTP logs, which start 32 minutes before its first card was signed. The fixes were tested by our suite and checked live from a throwaway key, and nobody outside has reviewed them. Ilja's results come from his issuance code, not from tokens captured off a live server, as he says himself. The Kanon and Tenuo posts are my readings until their maintainers answer.
