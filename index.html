Governance infrastructure for the agent economy.

Agent Passport System (APS) is an Apache 2.0 open protocol that gives every agent a verifiable identity, ties it to the person or company it represents, and enforces the scope, budget and conditions of its authority.

Every permitted action gets a signed receipt. Every denied action leaves evidence.

§ 1How it works

Authority flows down, evidence flows back.

Authority flows down. Each step narrows scope. Every action produces a signed artifact the principal can verify later, without trusting any party in the chain.

§ 8Frequently asked

Questions and short answers.

Q.1 How is APS different from OAuth or OIDC? +
OAuth authorizes a session for an application. APS authorizes an agent's actions and binds them back to a principal. Authority narrows monotonically at each delegation. Every permitted action produces a signed receipt. Every denied action leaves cryptographic evidence. OAuth answers "is this app allowed in." APS answers "what is this agent allowed to do, on whose behalf, with what proof."
Q.2 How does APS compose with MCP and A2A? +
APS runs underneath, not as a replacement. MCP exposes tools; APS records who used them under what authority. A2A coordinates agents; APS attributes the resulting work. An MCP server can check a passport before serving a call. An A2A handoff can pass a delegated passport with narrowed scope.
Q.3 What does an APS passport actually contain? +
A signed identity for the agent, the principal it acts for, the scope and conditions of its authority (which resources, what budget, until when), the chain of any prior delegations narrowing it further, and an Ed25519 signature from the issuer. Verification is offline — a service can check a passport's authority chain without contacting an issuer.
Q.4 How does revocation work? +
Three layers. Every passport carries expiry fields, so unused delegations time out automatically. A principal can issue a signed revocation that cascades through every delegation derived from the revoked passport. Gateways consult a revocation registry as part of the hot-path verification before allowing an action. Keys can be rotated; old delegations stop verifying the moment the revocation is signed.
Q.5 What does APS not protect against? +
APS proves an action was authorized by a chain ending at a principal. It cannot detect a principal who issues a malicious delegation deliberately, a gateway colluding with an agent against its principal, or a service that doesn't check passports. It defends against forged authority, scope creep, undeclared agents, after-the-fact denial of authorization, and silent attribution loss.
Q.6 What's the latency overhead in production? +
End-to-end gateway check, including TCP, signature verification, scope evaluation, and receipt persistence: 822µs p50 on bare-metal Linux (EPYC 7313P), 305µs on Apple M3, 1.07ms on AWS c7i.2xlarge. The pure verifier hot path runs in 420ns on bare-metal — the gateway loop is dominated by I/O, not verification. Reproducible at commit 6e258f4 under benchmarks/prototype-1/results/.
Q.7 Is APS production-ready today? +
The protocol specification is submitted as an IETF Internet-Draft. The TypeScript SDK ships on npm, Python bindings on PyPI, MCP server live at mcp.aeoess.com. The reference gateway runs as dogfood infrastructure. 2,966 SDK tests pass, plus 191 separate tests on the Rust verifier reference. Not yet externally audited. Status tracked in the README and roadmap.
Q.8 What's the relationship between APS and the AEOESS Gateway? +
APS is the open protocol: the spec, the SDKs, the MCP server, and the conformance suite, all Apache 2.0. AEOESS Gateway is the commercial enforcement product. The protocol is fully usable without the gateway. Any compliant implementation can issue passports, narrow delegations, and verify receipts.
