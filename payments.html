Payments

Spending controls, six payment rails, agent-to-agent settlement under signed delegation.

Who this is for

Fintechs, marketplaces, B2B platforms, and any company whose agents move money on behalf of users. If your agent triggers refunds, posts charges, runs procurement on company cards, or settles invoices, you need a protocol for which agent under which delegation with which spend cap on which rail.

Most stacks today log agent payment activity to Stripe or Plaid and reconcile after the fact. Revocation means killing the human's card. AEOESS is the layer above the rails: scoped delegation, signed receipts on every action, cryptographic denial when the agent steps outside scope.

The six rails

All six adapters share one PaymentRail interface, one canonical spend-limit resolver, and one denial vocabulary base. Each rail extends the base with rail-specific reasons.

Foundation / Nano reference

Ed25519-signed PaymentReceipt and PaymentDenial. The reference adapter every other rail composes against. Nano cryptocurrency settlement included for end-to-end demos.

AP2 google

Google Agent Payments Protocol v0.2 mandate crosswalk. Intent, Cart, Payment, and OpenPayment mandates issued under V2Delegation scope. aps_action_ref binds each mandate to the originating action.

x402 coinbase

HTTP 402 Payment Required protocol. Facilitator-mediated EIP-3009 USDC settlement on Base. The agent reads a 402 challenge, the rail evaluates scope, signs an authorization, and submits to the facilitator.

Stripe Issuing card

Webhook gating for agent-scoped virtual cards. Stripe authorization webhook hits the rail, the rail checks the delegation, returns approve or decline with a signed receipt.

ACP checkout

Agent commerce protocol: pre-authorize a checkout session, sign the session state, evaluate caller-supplied delegation against merchant terms. Tier-2 denial vocabulary covers merchant_not_allowed, currency_mismatch, idempotency_conflict, six more.

MPP multi-party

Draft httpauth-payment-00. Multi-party payment with HTTP challenge, scope-bound authorization, and replay protection. Maps cleanly to the foundation taxonomy via the Tier-2 crosswalk.

4-gate spending controls

Every rail evaluates the same four gates before allowing a payment. A delegation that fails any gate gets a signed denial with the matching reason.

Cap
Spend limit in cents, resolved canonically across V2Delegation forms.
Currency
Allowed currency set checked against rail support and delegation scope.
Counterparty
Merchant or recipient checked against allowed list (rails that carry merchant identity).
Time
Delegation valid_until and rail-specific freshness windows.

How it looks in code

Below is an ACP checkout pre-authorization. Same shape applies to MPP, Stripe Issuing, and the others.

// 1. Caller passes a V2Delegation with commerce scope and spend cap
// 2. ACP rail evaluates the delegation against the requested checkout
// 3. Returns either an AcpReceipt (signed approval) or AcpDenial (signed reason)

import { preAuthorizeAcpCheckout } from 'agent-passport-system/v2/payment-rails/acp'

const result = await preAuthorizeAcpCheckout({
  delegation,                          // V2Delegation, commerce scope, spend_limit_cents
  request: {
    merchant_id: 'shop_acme',
    line_items: [{ sku: 'sku_42', quantity: 1, unit_amount_cents: 4500 }],
    currency: 'usd',
  },
  issuerPrivateKeyHex,
  issuerPublicKeyHex,
})

if (result.kind === 'denial') {
  // result.denial.denial_reason: 'spend_limit_exceeded' | 'merchant_not_allowed' | ...
  // result.denial.signature: Ed25519 over the canonical denial
  return result.denial
}

// result.receipt: signed AcpReceipt with session_state, signer_did, signature
// Bind the receipt to your audit trail; the verifier on the merchant side
// can independently validate without trusting your gateway.
return result.receipt

What rail receipts do not prove

Honest scope on every receipt. A signed PaymentReceipt proves a payment instruction reached the rail under a specific delegation and the rail returned the recorded outcome. It does not prove:

  • The recipient earned the value (use an AttributionReceipt; out of scope here)
  • The contribution backing the payment was valid
  • Settlement is final (rails carry refund, dispute, and chargeback windows)
  • The counterparty's legal identity is what they claim

This negative semantic is codified in the type-level documentation on every rail receipt. Audit pipelines that aggregate rail receipts into bundles must enforce the distinction: a PaymentReceipt in a bundle says money moved on the rail, not that the recipient earned it.
