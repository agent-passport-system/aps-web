Enterprise

Identity, delegation, mutual auth, charter governance, and gateway enforcement for internal agent fleets.

Who this is for

Companies running internal agent fleets across engineering, ops, legal, finance, sales, and support. Teams that need scoped delegation, mutual auth between agents and internal services, charter-bound treasury operations, and an enforcement boundary that survives one agent compromising another.

Most enterprise agent stacks are an identity mess. Some agents on did:key, some on SPIFFE, some on OAuth, some unidentified. Delegation is loose: an intern AI gets prod access; the same key signs across teams. Revocation means hunting down which keys were used where. AEOESS is the protocol layer above that mess.

Bring your own identity

No identity rip-and-replace. AEOESS composes with the identity stack you already run. Identity is the input; scoped delegation, gateway enforcement, and audit are what we add on top.

did:key did:web SPIFFE / SPIRE OAuth 2.0 did:aps (native)

What we ship

Scoped delegation

Authority chains that can only narrow. Each delegation declares scope, spend limit, max depth, and validity. Sub-delegation strictly contained by the parent. Cryptographically enforced, not policy-enforced.

Gateway enforcement

Policy evaluation under 2ms. Every action evaluated against 14 constraint dimensions. Allow, deny, or escalate, with a signed receipt either way. The gateway is the boundary your agent fleet runs through.

Mutual auth

Agent-to-service handshake against a TrustBundle. Both sides verify the other's identity before exchanging anything. Composable with existing mTLS, but adds delegation context to the session.

Charter and office governance

Treasury operations, board votes, multi-class threshold approvals. Office holders have signing authority bound to their role; the role survives the holder. For companies, foundations, DAOs, and any structure that outlives its individuals.

Cascade revocation

Compromise an agent's key, revoke once, and the cascade kills every downstream sub-delegation. Audit captures the propagation. Compatible with planned and emergency key rotation paths.

Earned reputation

Trust scoped to context. An agent's reputation in code_review does not bleed into commerce. Bayesian scoring with per-scope priors; resists reputation-laundering attacks.

Posture overlay

Five tiers from full_trust to quarantine. Posture degrades on incident; recovery is gated. Verifiers see posture at issuance time so legacy receipts can be re-evaluated under newer scrutiny.

Human escalation

Per-action-class escalation requirements. High-value spends, schema migrations, irreversible actions all gate on owner confirmation. Confirmation is signed evidence, not a chat message.

How a fleet is set up

1
Charter ratified. Offices declared (CEO, CFO, Treasurer, Engineering Lead). Each office has signing scope and incompatibility rules (the same key cannot hold conflicting offices).
2
Office holders endorse the agents that act on their behalf. endorseAgent() creates a signed chain: principal → office → agent.
3
Each agent receives scoped delegations: code_review with depth 2, commerce with spend cap, data_access with TTL. Sub-delegation lets agents hand work down without widening authority.
4
Every action passes through the gateway. The gateway resolves identity, walks the delegation chain, runs the values floor, checks posture, and emits a signed receipt.
5
Compromise detected? revokeDelegation(id, { cascade: true }). The cascade propagates. Receipts emitted before revocation remain valid for compliance; new actions deny.

How it looks in code

Below is the gateway evaluation path. Same pattern works whether the identity is did:key, SPIFFE, OAuth, or native APS.

// Gateway evaluation: agent intent in, signed allow/deny out.
// Under 2ms across 14 constraint dimensions.

import { evaluateIntent } from 'agent-passport-system'

const result = await evaluateIntent({
  agentId: 'agent:claims-processor-7',
  delegation,                          // V2Delegation, signed chain
  intent: {
    type: 'data:read',
    target: 'datasource:claims-prod',
    purpose: 'audit_replay',
  },
})

if (result.decision === 'deny') {
  // result.denial_reason: 'no_data_scope' | 'time_window_violation' | ...
  // result.denial_domain: 'authority_scope' | 'temporal_integrity' | ...
  // Signed denial receipt; verifier can independently validate.
  return result.denial
}

// result.action_receipt: signed proof of allow.
// Bind it to the action; downstream consumers can verify the chain.
return result.action_receipt
