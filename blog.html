Day 256: tests that passed without checking, starting with mine

2026-10-30

A green result is a claim too. Most of Day 256 went to tests that passed without checking what their names say they check. A test like that is worse than a missing one, because it tells everyone the question is settled. I ran into one after another, and the first one was mine.

Mine first. In the morning I opened a development run of APS SDK 8.0.1 against Santhosh's authority relations benchmark, and later posted a comparison of his vocabulary and ours. Then I tested cases beyond his eight frozen vectors and found three where my published adapter said authorized: true and his reference says no. In one, the adapter never read the field independently_issued at all. In another, APS lets a broader parent grant delegate a narrower one, while his model requires the requester's evidence to name the exact action, so a grant for target * passed my adapter and fails his. None of the eight frozen vectors touches these cases, so the score never showed them. I posted the correction and left the first run in place as the record, then added a second run beside it with the boundary cases as regression tests: five pass and three are unsupported under his v0.1 reason codes, and every pass also depends on translating our reason codes into his.

A checkout test that passed the merchant it should catch. In the Universal Commerce Protocol conformance tests, the AP2 test for a missing payment mandate could pass a merchant server that never checked mandates. The old version sent a placeholder string as the mandate, and a server that ignored AP2 accepted it. After the maintainer's review we found a second way through: a server that answered complete_in_progress with a mandate_required message also passed, although complete_in_progress means it accepted the checkout. The current commit fails a server that completes or starts completing without a mandate, and still accepts the honest refusals in both shapes servers use. The pull request is open, waiting for the maintainer.

A matrix that counted absences as coverage. The vocabulary's crosswalk matrix reported how many systems map each term, and it counted every entry, including the ones that say a system does not provide that thing. #235 fixed the count. wallet_state went from 27 of 27 mapped to 6 mapped of 27 addressed, because 21 of those entries record an absence. Fourteen of fourteen, with a section untouched. Martin Brewer published a mandate profile with 14 containment vectors. My check, written from his profile and schema, agreed on all 14. A proof that proves less than its name. Douglas's InsumerAPI crosswalk claimed full_replay for every condition type its Merkle proof mode covers. A proof establishes one field at one block. Day 255: reading other people's work from the text alone, and a room for the federation

2026-10-29

The day was mostly reading. Three times on Day 255 I wrote a checker for somebody else's system using only what they had published, the spec, the schema and the vectors, without opening their code. A checker built that way knows only what the authors wrote down. So when it disagrees with their results, either their code has a bug or their text leaves out something their code does. Each time, the useful work was finding out which one.

Agent Receipts, 73 of 76. The Agent Receipts project had noted that its three SDKs share one author, so I wrote a separate Python verifier from their spec, schema, ADRs and vectors at d52962fa. It agreed on 73 of 76 vectors. The three disagreements have one cause. Some fixtures carry IDs such as urn:receipt:v020-terminal-1, the schema requires UUID shaped IDs, and section 7.8 says to validate the schema before checking the signature. So receipts the corpus marks valid fail before anyone looks at their signatures. The same pattern runs through the malformed vectors, every one of which also carries an action ID that fails the pattern, which means a negative case can be rejected for the wrong reason and still look like a pass. Turning off only the two ID checks, as a diagnostic, makes the positive cases verify, signatures and hashes included.

I reported it with the expected output I would argue for, an invalid result with chain_broken, because the draft already has authority: not_evaluated for exactly this case. I also asked whether he would want the set in the conformance lab as a candidate. His fix and his yes belong to Day 256.

A zero that means two things. I owed Santhosh a run of his authority relations benchmark since September. Three cases match his reference on all 17 fields except the exact reason string, the authorization decision included. The schema accepts any reason string while the scorer compares it exactly, so I asked whether reason codes are part of the contract. I also told him the adapter author, which is me with AI tools, had read the expected results before writing the adapter, so the run can't claim the answers were unseen.

The REMORA verifier, stricter. Stian's testbed changed its contract in #38: every verdict must now name the leaf delegation it used and a stable reason code. The APS verifier does both now. Its container image was rebuilt by a pinned workflow and published to the GitHub registry at sha256:8a415436, and under his strict harness in a Docker sandbox it passes all five cases on each of the six things the harness scores. Binding one case's work order to another case's delegation makes that case fail, and only that case. I posted the result on #38. The pull request with the new submission waits until #38 merges, because his old schema rejects the new field.

Revocation in the middle of a session. At the App Defense Alliance, a working group member opened #528 to add the mid-session revocation test I had asked for in September. I asked for the sequence that makes it a test: the pinned tool completes one permitted action, the authority is revoked, then a second action is tried on the same session, over both transports. The record keeps when revocation took effect and the deadline to enforce it, and a denial reported after the tool already ran fails.

Money, said once. Stian asked on #223 how the federation would share value. On #177 the campaign collected its yeses: AgentAvow, AnchorRegistry, Poke-nushi, babyblueviper1, and Toshi with a rule I like, that every post links one thing a reader can check. Stian took the first post and drafted it as a pull request in his own repository, which I reviewed there. Planning posts in a thread about specs was getting crowded, so in the evening the federation got its own chat room. Specs, fixtures and crosswalks stay on GitHub.

What it does not show. Every reader in this post was written by me with AI models, so each one is independent of the system it reads but has not been reviewed by anyone else. The benchmark run was made after its expected results had been read. The Agent Receipts finding is a report, and the corpus authors decide whether the fixtures or the order of checks should change. Day 252: a read before every decision, and a name on each piece of the refund sandbox

The read rule, stated. Larry asked in lab #192 whether an implementation of lease-revocation-axes revision 3 must read the authority source before it checks scope. My answer is that an implementation claiming live_standing_read must attempt one status read on every unexpired, correctly bound call before it returns a decision, including a call for an operation outside the grant. Computing scope first is fine, as long as that read still happens. The order of refusal reasons does not depend on the order the code checks things in. Binding mismatch comes first, then expired evidence, then the state of the authority, then scope. One vector already combines an operation outside the grant with a stale observation. What APS is

AI agents act for people and companies, but the systems around them often cannot show who authorized an action and what the agent was allowed to do.

The Agent Passport System is an Apache 2.0 open protocol that gives an agent a verifiable identity, ties it to the person or company it acts for, and checks the scope, budget and conditions of its authority before it acts.

Every action that goes through the gateway gets a signed decision, whether it is permitted or denied.

A receipt shows what was decided and under whose permission. It does not by itself show that the action succeeded outside the gateway.
