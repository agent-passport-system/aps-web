Protocol

How APS works

An agent can only do what someone allowed it to do. APS checks that before the action happens and signs the answer.

One check, two answers

Example
You allowPay the electric bill, up to $200
Agent asksPay $150
Gateway checks$150 is inside $200
Allowedsigned decision
Agent asksPay $250
Gateway checks$250 is over $200
Refusedsigned decision

The gateway decides before the payment runs, so a refused payment never starts. Both answers are signed, so anyone with the record can check what was decided and which permission it used. A signed "allowed" shows the decision, not that the bill was actually paid.

Passing it on

An agent can hand part of its work to another agent, but it can only hand over less or the same, never more than it holds.

  1. Youup to $200
  2. Agent Aup to $200
  3. Agent Bup to $50valid, it is less
  4. Agent Bup to $500invalid, A never had $500

If you cancel what you gave Agent A, everything A passed on is cancelled with it.

Three rules

  1. 1Permission only shrinks

    Each handoff can keep a limit or cut it, never raise it. This holds for money, time, what the agent may touch and how many more times it can pass work on.

  2. 2Checked before it happens

    The gateway decides before the action runs. If it cannot confirm the permission, for example because a record is missing, the answer is no.

  3. 3Every answer is signed

    The agent signs what it asked for. The gateway signs what it decided and what it saw happen. Anyone can check those signatures later.

The gateway can only check actions that go through it. If an agent has another way into a system, APS does not see that path.

The seven limits on every permission §4.1

Every permission record carries exactly seven limits. A missing limit makes the record invalid, it never means unlimited. A handoff is valid only when every limit is no wider than its parent's.

  • 1Scopewhat the agent may do

    Every grant in the child must be covered by a grant in the parent.

  • 2Spendper action and cumulative limits, in one unit

    Limits can only go down, the unit cannot change, and a bounded parent cannot produce an unbounded child.

  • 3Depthhow many more hops it may delegate

    Each hop uses up at least one. A parent with none left cannot delegate.

  • 4Timethe validity window

    The child window must sit inside the parent window.

  • 5Reputationthe reputation ceiling

    The ceiling cannot rise.

  • 6Valuesvalue identifiers the agent must hold to

    The child keeps every identifier its ancestors required.

  • 7Reversibilityhow irreversible an action may be

    The ceiling cannot move toward less reversible.

A full purchase from the draft §9.11.1

A principal gives a procurement agent authority to buy. The procurement agent hands one supplier to a subagent, and each limit in the subagent's copy is the same or narrower.

LimitPrincipal to procurement agentProcurement agent to subagent
Scopecheckoutcheckout from one supplier's catalogue narrower
Spend per actiona set limita lower limit narrower
Spend cumulativea set limitat or below the parent's same or narrower
Depth2 hops left1 hop left narrower
Timeuntil the end of the quarterinside that window same or narrower
  1. IntentThe subagent signs an action intent that names its delegation and commits to the exact purchase.
  2. DecisionThe boundary checks the chain from root to leaf, issues a permit and reserves the amount against the running total.
  3. DispatchJust before dispatch the boundary checks time and revocation again and consumes the decision, so it cannot be used twice.
  4. ResultThe boundary records the result it observed, with a reference to the effect.
The three signed records §5
  1. signed by the agentAction intent

    What the agent wants to do, under which delegation, committed by digest.

  2. issued by the boundaryPolicy decision

    Permit, deny or narrow. A narrow carries the reduced authority and the constraints applied.

  3. issued by the boundaryAction result

    The execution result the boundary observed, when the action was dispatched.

The decision and the dispatch are two steps. A permit is checked again and consumed when it admits the action, so it cannot be replayed or used after its authority has ended. A valid signature or chain is not proof that an outside event happened §2.2, and APS does not establish that no other credential reached the target outside the governed path §2.5.

Six verdicts and eight invariants §2.3 §4.6

A verifier reports one of six verdicts about a permission record, each with a reason code. It describes what the verifier can conclude from what it holds, not what happened in the world.

  • validthe artifact currently confers the authority claimed
  • invalidit does not, or no longer does: revoked, expired, exhausted, or under an invalid ancestor
  • not establishedthe verifier cannot reach a conclusion, which is never a finding about the world
  • not yet effectivevalidly issued, and an enabling condition has not happened yet
  • suspendeduse is paused by one or more live causes
  • restrictedauthority continues in reduced form under a live constraint

Narrowing, spend and signature integrity are enforced when a delegation is issued as well as when it is verified, so an issuer refuses to sign under an expired or revoked parent.

  • INV-1Identity verifiability
  • INV-2Scope monotonic narrowing
  • INV-3Spend limit narrowing
  • INV-4Cascade completeness
  • INV-5Revocation irreversibility
  • INV-6Intent and receipt binding
  • INV-7Authority attribution completeness
  • INV-8Signature integrity

The older Delegation API

The SDKs still ship an older Delegation record for compatibility, and it is not the same as AuthorityDelegationV1. An erratum of 2026-08-17 noted that the verifiers compared spend and depth only when both parent and child carried the field. AuthorityDelegationV1 closes that gap because all seven limits are required and every one is compared, including containment of the validity window. The older Delegation API still compares an optional field only when it is present, so new integrations should use AuthorityDelegationV1. The authority documentation describes both.

Extensions outside the draft
  • Commerce preflight

    Payment checks for passport, scope, spend limit, merchant allowlist and idempotency, with a human approval threshold.

  • Reputation

    Scoring that a deployment can use for the reputation limit.

  • Beneficiary attribution

    Crediting work back to the person or organization an agent acts for. This is companion work, and its API has moved to the gateway package.

  • OAuth ID-JAG

    The TypeScript SDK can take an already verified ID-JAG grant as the root of an APS delegation. It is pinned to ID-JAG draft -04 and does not verify the grant itself.

Cross-engine receipt interop has been demonstrated with VeritasActa and protect-mcp. Known limits are in the threat model.

What APS is

AI agents act for people and companies, but the systems around them often cannot show who authorized an action, what the agent was allowed to do, and what actually happened.

The Agent Passport System is an Apache 2.0 open protocol that gives an agent a verifiable identity, ties it to the person or company it represents, and checks the scope, budget and conditions of its authority before it acts.

Every permitted action gets a signed receipt, and every denied action leaves evidence.

Each receipt also records who the agent acted for, so the work, value and outcomes it produces stay attributed to the person or company behind it.
