Protocol

Agent Passport System protocol

Verifiable identity. Scoped authority. Enforcement before execution. Signed evidence.

AI agents increasingly act on behalf of people and organizations. They call tools, make purchases, read sensitive data and hand work to other agents. A valid identity tells a system who is making a request. It does not establish whether that agent has the authority to do what it asks.

The Agent Passport System (APS) gives that authority a signed, verifiable form, lets it pass from agent to agent without growing, and checks it at the point where an action is admitted. The record formats and verification rules are specified in an individual IETF Internet-Draft, which is not an IETF standard. The code is Apache 2.0.

How it works

  1. 1Establish identity and authority

    An agent has a cryptographic identity. A person or organization binds that identity to itself with a separate signed record, and issues a signed delegation that sets the agent's scope, spending limits, validity window and other constraints.

  2. 2Delegate without widening

    An agent can delegate work to another agent, but the recipient never gets more authority than its parent held. A verifier checks the chain and every limit in it, including whether an ancestor has expired or been revoked.

  3. 3Check before execution

    The enforcement boundary evaluates one delegation chain and the applicable policy before the action is dispatched. A request outside the authority is denied, and evidence that is missing or unavailable never becomes permission.

  4. 4Leave verifiable records

    The agent signs its intent. The boundary signs its decision and, when the action is dispatched, the result it observed. Anyone can check those signatures against their own trust policy. A signed decision does not, by itself, show that an outside action completed.

One purchase, step by step

The draft's own worked example, §9.11.1

A principal gives a procurement agent authority to buy. The procurement agent hands one supplier to a subagent. Each line below is one facet of the authority, and the subagent's copy is always narrower.

FacetPrincipal to procurement agentProcurement agent to subagent
Scopecheckoutcheckout from one supplier's catalogue narrower
Spend per actiona set limita lower limit narrower
Spend cumulativea set limitat or below the parent's same or narrower
Depth2 hops left1 hop left narrower

  1. IntentThe subagent signs an action intent that names the child delegation and commits to the exact purchase.
  2. DecisionThe boundary checks the chain from root to leaf, issues a policy decision with the verdict permit, and reserves the amount against the running total.
  3. DispatchJust before dispatch the boundary checks time and revocation again and consumes the decision, so it cannot be used twice.
  4. ResultThe boundary records the result it observed, here succeeded, with a reference to the effect.

If the subagent's grant had been wider than its parent's, the chain would be invalid with scope_not_covered. If the subagent also held a second chain from an unrelated principal, the two would never be combined: each action uses one chain.

The authority model

Seven facets, §4.1

Authority is a record with exactly seven facets. A missing facet makes the record invalid, it never means unlimited. A child is valid only when every facet is no wider than its parent's.

  • 1Scopewhat the agent may do

    Every grant in the child must be covered by a grant in the parent.

  • 2Spendper action and cumulative limits, in one unit

    Limits can only go down, the unit cannot change, and a bounded parent cannot produce an unbounded child.

  • 3Depthhow many more hops it may delegate

    Each hop uses up at least one. A parent with none left cannot delegate.

  • 4Timethe validity window

    The child window must sit inside the parent window.

  • 5Reputationthe reputation ceiling

    The ceiling cannot rise.

  • 6Valuesvalue identifiers the agent must hold to

    The child keeps every identifier its ancestors required.

  • 7Reversibilityhow irreversible an action may be

    The ceiling cannot move toward less reversible.

Six verdicts §2.3

A verifier reports one of exactly six verdicts about an authority record, each with a reason code. It describes what the verifier can conclude from what it holds, not what happened in the world.

  • validthe artifact currently confers the authority claimed
  • invalidit does not, or no longer does: revoked, expired, exhausted, or under an invalid ancestor
  • not establishedthe verifier cannot reach a conclusion, which is never a finding about the world
  • not yet effectivevalidly issued, and an enabling condition has not happened yet
  • suspendeduse is paused by one or more live causes
  • restrictedauthority continues in reduced form under a live constraint

Eight invariants §4.6

Narrowing, spend and signature integrity are enforced when a delegation is issued, not only when it is verified, so an issuer refuses to sign under an expired or revoked parent.

  • INV-1Identity verifiability
  • INV-2Scope monotonic narrowing
  • INV-3Spend limit narrowing
  • INV-4Cascade completeness
  • INV-5Revocation irreversibility
  • INV-6Intent and receipt binding
  • INV-7Authority attribution completeness
  • INV-8Signature integrity

Enforcement and records

Policy chain §5, records §7
  1. signed by the agentAction intent

    What the agent wants to do, under which delegation, committed by digest.

  2. issued by the boundaryPolicy decision

    Permit, deny or narrow. A narrow carries the reduced authority and the constraints applied.

  3. issued by the boundaryAction result

    The execution result the boundary observed, when the action was dispatched.

The decision and the dispatch are two steps. A permit is checked again and consumed at the moment it admits the action, so an approval cannot be replayed or used after its authority has ended.

What the records do not establish

  • A valid signature, receipt or delegation chain is not proof that an outside event happened or that a signed claim is true §2.2.
  • APS establishes that a governed path was valid. It does not establish that no other credential reached the target system outside that path §2.5. A missing record of an ungoverned path is not evidence that none was used.
  • The boundary can enforce only what is routed through it.

The older Delegation API

The SDKs still ship an older Delegation record for compatibility, and it is not the same as AuthorityDelegationV1. An erratum of 2026-08-17 noted that the verifiers compared spend and depth only when both parent and child carried the field. For AuthorityDelegationV1 that gap is closed: all seven facets are required and every one is compared, including containment of the validity window. The older Delegation API still compares an optional field only when it is present, so new integrations should use AuthorityDelegationV1. The authority documentation describes AuthorityDelegationV1 and how its scope rule differs from the older format.

    Crediting work back to the person or organization an agent acts for. This is companion work, outside the draft, and its API has moved to the gateway package.

  • OAuth ID-JAG

    The TypeScript SDK can take an already verified ID-JAG grant as the root of an APS delegation. It is pinned to ID-JAG draft -04 and does not verify the grant itself.

    The MCP server exposes the protocol to MCP clients.

What APS is

AI agents act for people and companies, but the systems around them often cannot show who authorized an action, what the agent was allowed to do, and what actually happened.

The Agent Passport System is an Apache 2.0 open protocol that gives an agent a verifiable identity, ties it to the person or company it represents, and checks the scope, budget and conditions of its authority before it acts.

Every permitted action gets a signed receipt, and every denied action leaves evidence.

Each receipt also records who the agent acted for, so the work, value and outcomes it produces stay attributed to the person or company behind it.
